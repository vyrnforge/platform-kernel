## 1. Apply the specification

Choose scope based on the operation, not the JAR:
- A: standalone primitives (IDs, contracts, references, correlation/health as used); no mandatory auth pipeline or database.
- B: authenticated tenantless operation; trusted identity and local resource authorization, never tenant-owned access or implicit deployment authority.
- C: tenant-scoped operation; exactly one active tenant, authoritative membership, effective entitlement and local authorization, tenant-filtered data access.
- D: optional JDBC, additive to scope; same product-owned transaction, applicable durable/replay/intent/worker controls. Core-only local durable persistence has the same applicable behavior obligations. D is not an authorization scope.

In the matrix, ALL means every adopting application (for the artifacts/contracts actually used); AUTH means B/C or any authenticated runtime path; TEN means tenant-owned access, including jobs/events/data; DUR means required durable mutation/intent or retry behavior, regardless of adapter; RET means retriable tenant-scoped API mutation; EVT means event producer/receiver/outbox as applicable; JDBC means selected Kernel JDBC; FILE means file-reference use; OPS means operational runtime as applicable; CHANGE means upgrade/migration; CROSS means existing #41 or applicable cross-consumer acceptance. Multiple applicability labels are alternatives unless expressly combined. A scenario is mandatory when applicable; not-applicable requires a reason and review, not merely omission of the JDBC JAR. No tenantless API mutation-idempotency support is implied by this contract. IAM DEPLOYMENT is distinct from TENANT and TENANTLESS under [ADR-0085](https://github.com/wyrmgate/iam/blob/main/docs/adr/0085-platform-kernel-adoption-boundary.md).

Record the application operation and scope, owning product and authority, actual selected artifact(s), data/transport and environment. Apply scenarios before authorizing adoption; missing real provider or production evidence remains a gap, even where a library test passed. Tests below are existing source-level anchors or future consumer evidence requests. No consumer test results are inferred from the scenario descriptions.

## 4. Evidence record and acceptance gate

One record per scenario and target revision (or linked equivalent records):
- Scenario ID, V-K trace, operation, scope and applicability (reason for N/A).
- Kernel coordinates/version and SHA-256 for each used artifact; source/tag for release or candidate; actual consumer commit, PR head/base and actual checked-out merge SHA where applicable; target Java/runtime, environment and dependency convergence.
- Preconditions, expected result, observed result, test command/name or static review, link to job/log/report and date; configuration/fixture version without secrets.
- Result: PASS = observed expected result at exact applicable target; FAIL = observed mismatch; STALE = previous evidence insufficient after material revision/artifact/environment change; MISSING = applicable evidence absent; N/A = justified non-applicability approved by owner/reviewer. HOLD is an acceptance disposition, not a test result. Synthetic or historical PASS remains scoped; never label current acceptance PASS from it.
- Responsible discipline, reviewer and independence status, product owner decision, unresolved risk, reopen condition.

A change to artifact, tested source/base, dependency graph, identity/authorization policy, transaction/storage schema, transport or deployment configuration reopens affected evidence. Record material delta and reverify applicable scenarios; preserve historical records. Unchanged content alone is not fresh runtime proof. All applicable mandatory scenarios must pass before the relevant acceptance gate; mandatory count excludes only justified N/A. No accepted unauthorized scope/replay/domain-boundary violations. Any exception requires separate explicit authority, not a fabricated pass.

## 5. Handoff and boundaries

QA owns specification/evidence classification; Security/IAM verifies trust, scope/replay and secrets; API/Integration verifies serialization and references; Backend/Data verifies actual transaction/lease/restore; Platform/Release verifies artifacts and packaging; Operations verifies actual environment and SLOs; Architecture confirms ownership and independence; product owners accept their own integrations. These are discipline assignments, not claims of named independent reviewers. #41 remains the existing cross-consumer verification workstream. No new issues or competing acceptance process. FAA-04/05 and later research need separate scope authorization.
