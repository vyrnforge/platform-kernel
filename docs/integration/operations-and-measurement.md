## 2. Operational indicators and action guide

Define the actual service journey and observation window before setting targets. For each indicator record source/query, inclusion/exclusion rules, aggregation, denominator, freshness and accountable owner. Missing or insufficient telemetry is UNKNOWN, not healthy or zero. Low traffic is reported with counts and observation window; zero eligible events gives N/A/insufficient data, not 100%. Select alerts based on approved objectives and impact, not library defaults. The following are proposed definitions, not installed metrics or approved SLOs.

| Indicator | Definition / denominator | First investigation or action | Owner |
| --- | --- | --- | --- |
| Availability / journey success | Successful eligible requests or completed journeys / eligible attempts over agreed window. Define expected client errors vs service failures and dependency-caused failure explicitly; report counts. | Check readiness, failed dependency, operation outcome and correlation; restore service or route to product incident owner. | Service owner/Operations |
| Latency and throughput | p50/p95/p99 of defined operation duration with sample count; eligible completed requests per time window. Separate success/failure and queue time where useful. | Correlate saturation, DB and dependency latency, pagination/limit behavior; review actual load evidence. | Operations/Backend |
| Dependency errors / saturation | Failed eligible dependency calls / attempted calls; connection pool/CPU/memory/queue capacity used versus configured capacity. | Identify failing dependency and bounded timeout/backoff; stop unsafe retries, do not restart solely for readiness failure. | Operations/Platform |
| Durable backlog | Count PENDING/PUBLISHED/DEAD by applicable safe scope; report PENDING with active lease separately, not as a fourth persisted status. Oldest pending age, attempts, publish success/failure and lost-claim count per window; use the actual selected adapter's state model. | Check worker availability, claim expiry, bounded batch/lease, transport failures; reconcile uncertain delivery before re-drive. | Backend/Operations |
| Replay and isolation | Replay/conflict/in-progress outcomes per retriable mutation attempt, unauthorized scope/replay violations count; investigate anomalous denial or unexpected success. | Check current authorization, fingerprint/tenant/target and transaction evidence; contain exposure without revealing other tenant data. | Security/QA/product |
| Recovery | Measured recovery time from agreed start to verified service/data readiness; actual recoverable data-point gap versus agreed RPO, plus reconciled/unresolved effects. | Keep admission held if objective or integrity not met; restore/reconcile with accountable Data owner and record retest. | Data/Operations |
| Telemetry completeness | Eligible operations with required safe correlation/outcome fields / observed eligible operations; missing data and collection lag reported. | Fix source/collection and privacy policy; never emit secrets or high-cardinality identifiers indiscriminately. | Operations/Security |

Structured logs include timestamp/level/service/environment/operation/outcome, request and correlation when applicable; tenant/actor only as permitted (Kernel safe defaults exclude both). Trace metadata remains opaque and distinct from business correlation. Do not use unbounded request/correlation/event IDs as metrics labels; use trace/log lookup instead. Liveness answers whether the process should run; readiness answers whether it can serve intended traffic. Probe exceptions expose safe codes, not raw exceptions. Product owns alert destination, severity, paging threshold, response window, escalation and incident commander; all remain TBD until actual environment/service objectives agreed.

## 3. Recovery and rollout decision recipes (planning only)

### R-01 — Upgrade or rollback with durable state

1. Identify current/target artifacts, migration checksums, schema version, deployed writers/publishers, owning transaction and supported rollback compatibility. For local persistence review its own migration; do not apply Kernel SQL to unrelated stores.
2. For Kernel JDBC stop/drain old publishers before V3 and old intent writers before 0.3.2 fingerprint writes; ensure no mixed old/new writer or dual store. Preserve immutable V1–V3. Separate migration/runtime credentials; restrict ordinary audit update/delete and TRUNCATE/DDL. Verify backup and recovery plan before authorized change.
3. Apply only approved migration sequence; start compatible writers, verify actual version, scoped read/write/replay, audit/intent and receiver consistency, health and rollback criteria. If uncertainty, hold traffic and reconcile rather than guessing success.
4. Never roll back schema destructively or run old binaries against new fingerprints without separately reviewed migration/recovery plan. A fresh JDBC installation does not need an old-writer migration rehearsal unless the rollout actually includes legacy state. Stop workers first, preserve all domain/reliability/audit data and reconcile pending, expired and uncertain deliveries. Prefer compatible roll-forward when rollback cannot preserve invariants. No actual upgrade or rollback executed here.

### R-02 — Lost response, expired lease or uncertain delivery

Identify tenant/operation/key/fingerprint (redact sensitive input), event ID and correlation. Reauthenticate/authorize current caller; inspect owning transaction and committed result. Within retention, use matching replay; conflict or in-progress are distinct; only acquired executes. Expiry permits reacquisition, so reconcile known effects before any unsafe retry. On rollback lease may remain IN_PROGRESS until explicit abort/expiry; no partial authoritative effect permitted. For leased outbox, stale worker cannot update newer claim; lostClaims indicates uncertainty, not proof of non-delivery. A DEAD row can have been delivered. Pause unsafe publisher/re-drive, reconcile receiver state with event ID and necessary product state, obtain authorized disposition, then bounded re-drive only where safe. Do not mutate audit history or pretend transport delivery is exactly once. Record what happened, observed effect, owner, remediation and retest.

### R-03 — Backup restore or service failure

In a separately authorized isolated target, record backup identity/time, recovery start, actual restored point and relevant artifact/schema versions. Verify domain rows, audit/intent/idempotency records and authoritative consistency, tenant boundaries, current authorization/replay and actual user journey; compare external receiver effects and reconcile recovery-point gaps before resuming traffic. Measure elapsed recovery and recoverable data gap against approved RTO/RPO. If objectives or observations are absent, report MISSING and keep admission HOLD; if measured results exceed objectives or integrity fails, report FAIL. Neither is PASS. Record actual recovery start/end, recovered point and evidence of reconciled gaps separately; an approved nonzero RPO does not authorize silently losing required intents. A backup or library CI result is not restore acceptance. Record unresolved discrepancies, owner and next exercise; no live restore/failure injection executed here.

## 4. Business measurement — Asset first, ITSM second

DEC-K025–029 and Delivery v0.6 require actual comparable evidence before targets or promotion. IAM/Storage are reference consumers, not forced migrations or automatic evidence of greenfield value. The unit of comparison is equivalent **technical foundation behavior**, not whole product delivery, feature count or library test count.

### Baseline design

- Asset owner + Product/BA select one separately approved real vertical slice (e.g. a tenant-scoped asset read/write journey with applicable identity, errors, correlation, audit/event intent and retry behavior). This is an illustrative measurement scope, not an authorized Asset implementation. Define mandatory CC cases and acceptance boundary before collecting data. ITSM later chooses equivalent foundation behaviors on its own service-management journey; normalize differences rather than treating different workloads as equal.
- Agree comparator before measuring: historical standalone implementation of equivalent behavior with auditable records, or a separately authorized bounded equivalent baseline. Document requirements, tools, team experience, starting infrastructure, exclusions, observation window and evidence quality. An estimate or synthetic fixture may inform planning but is not an observed baseline; if no credible comparator exists report UNKNOWN. Do not build a duplicate full application solely to create a baseline.
- Track actual engineering time by activity (setup, integration/config, adapters, verification, debugging/rework, migration, shared maintenance, local maintenance/operations); separate business-domain work and waiting/calendar duration. Record source (work log/PR/issue/time record), units and accountable owner; no secret/customer payload.
- Capture first conformant endpoint when its applicable mandatory cases pass at exact artifact/revision and owner acceptance is recorded, not when code compiles. Measure both comparable arms over agreed windows; account for learning, changed requirements, and reused infrastructure. Avoid double-counting shared maintenance/cost or savings across consumers.
