## What changes from published v0.3.2?

| Area | Proposed v0.4.0 change | Consumer action |
| --- | --- | --- |
| Tenantless access | Add `RequestContextPipeline.tenantless(identityAdapter, domainAuthorizationHook)`. Existing four-port constructor remains. | Optional convenience for **authenticated** non-tenant-owned actions; keep real identity verification and product-owned resource authorization. |
| Module keys | Share the published v0.2 module-key grammar: `^[a-z][a-z0-9_.:-]*$`, maximum 128 characters. The registry now accepts conforming namespaced keys; tenant-scoped endpoint policy rejects invalid keys earlier. | Inventory existing module IDs and negative-path behavior. This is not a new permission system. |
| Idempotency request | `IdempotencyRequest` rejects overlength `operation` (192), `key` (512) and `requestFingerprint` (512), measured in Unicode **code points**. Operation must also match `^[a-z][a-z0-9_.:-]*$`. | Validate inputs and error mappings before persistence. Previously invalid-overlength values may now fail at construction. |
| Optional JDBC JSON codec | Add `JacksonRecordCodec(ObjectMapper)`; the no-arg constructor remains. Supplied mapper is copied; default typing is disabled; map key ordering is deterministic. | Only opt in after stored JSON, fingerprint, historical replay and DTO-policy compatibility tests. |
| Integration and testing | More explicit HTTP duplicate-header, safe transaction, host-Flyway coexistence, synchronous health-probe and Java source-hygiene guidance/tests. | Adopt relevant documentation and negative tests. No framework starter, runtime service or required database is added. |

**Unchanged boundaries:** Java 21 minimum; embedded library; Maven group `io.github.vyrnforge`; Java package `io.vyrnforge.platform.kernel.*`; same three JARs; core without mandatory third-party runtime dependencies; optional PostgreSQL/Flyway/Jackson adapter; testkit in test scope; immutable released wire contract v0.1/v0.2 schemas and Flyway V1–V3 scripts. IAM/IdP, File Storage, database ownership, event delivery, SLOs and business authorization remain outside the Kernel.

## 2. Authenticated tenantless endpoints (new optional factory)

**When:** A verified user or service accesses an explicitly global, non-tenant-owned resource. **Not when:** the handler reads or mutates tenant-owned data, even if its route looks global.

~~~java
// Integration excerpt: trustedIdentity is produced by the application's REAL
// authenticator (native IAM or supported external IdP); not from raw headers.
var pipeline = RequestContextPipeline.tenantless(
    new ValidatedIdentityAdapter(),
    (actor, action, resource) ->
        actor.authorization().hasPermission(action)); // Product-owned example policy

var resolved = pipeline.resolve(new RequestContextInput<>(
    trustedIdentity,
    TenantContext.none(),
    CorrelationContext.create(),
    EndpointPolicy.tenantless("profile.read"),
    null)); // Only when no tenant-owned resource is involved
~~~

Imports: `io.vyrnforge.platform.kernel.pipeline.*`, `io.vyrnforge.platform.kernel.context.*`, and `io.vyrnforge.platform.kernel.identity.ValidatedIdentityAdapter`.

**Kernel provides:** A factory that supplies deny-by-default tenant-membership/entitlement ports to the existing pipeline, saving unused wiring on tenantless-only consumers. It still performs identity-adapter authentication, refuses an active tenant on a tenantless endpoint, and invokes the application authorization hook.

**Your application provides:** Actual token/session verification before constructing a validated credential, stable issuer/subject mapping, an action/resource policy, and any resource lookup. The example lambda is illustrative, not a universal permission policy.

**Verify:** A valid trusted profile request succeeds; forged/unverified credentials fail; denied permission fails; supplying `TenantContext.tenant(...)` to a tenantless policy fails; a tenant-owned resource fails; and `EndpointPolicy.tenantModule(...)` cannot be used to bypass membership/entitlement using this factory.

**Existing path still works:** Use the original four-port constructor for tenant-scoped requests (authoritative membership, module entitlement and domain authorization). Published v0.3.2 consumers must continue to use that constructor, because the factory is not available in their JAR. A complete synthetic candidate-source walkthrough is [`verification/GeneralUsageExample.java`](https://github.com/vyrnforge/platform-kernel/blob/f8cbdfe983d951e40d050b6a83c7c1ff1d065ab3/verification/GeneralUsageExample.java); its fixtures do **not** verify real IAM.

## 3. Module entitlement and request input validation

~~~java
// v0.4.0 source-level examples, not runnable against published v0.3.2.
var module = new ProductModule("asset.inventory:read");
var policy = EndpointPolicy.tenantModule("asset.inventory:read", "asset.read");
ModuleKeys.require("asset.inventory:read"); // Valid key grammar
// ModuleKeys.require("ASSET");  // IllegalArgumentException
~~~

Use `io.vyrnforge.platform.kernel.module.ProductModule`, `ModuleKeys` and `io.vyrnforge.platform.kernel.pipeline.EndpointPolicy`. A module's *registration* identifies a known module; *entitlement* controls enabled availability per tenant; and the resource-owning application still decides *authorization*. Test all three separately.

For retriable mutations, `IdempotencyRequest(tenantId, operation, key, requestFingerprint, expiresAt)` now fails before JDBC on blank, invalid or overlength fields. `tenantId` must remain a canonical UUIDv7; `expiresAt` must be present (and future when `begin` acquires the key). The application defines a stable, actor/target/payload-aware fingerprint—Kernel does not derive it automatically. Validate Unicode code-point limits, same-key/same-effective-request replay, different-fingerprint conflict, concurrent retry, expiry and current authorization for every attempt.

## 4. Optional JDBC codec and reliability (candidate-only API)

~~~java
// Integration excerpt: JDBC adapter must be selected; this constructor
// does not exist in the published v0.3.2 JAR.
ObjectMapper appMapper = new ObjectMapper();
// Register carefully reviewed modules/DTO settings here if required.
JacksonRecordCodec codec = new JacksonRecordCodec(appMapper);
~~~

Imports: `com.fasterxml.jackson.databind.ObjectMapper` and `io.vyrnforge.platform.kernel.persistence.jdbc.JacksonRecordCodec`. The no-argument constructor remains the default. The new constructor copies the mapper and disables default typing; it does *not* transform Java records into the public snake_case `EventEnvelope`/audit wire schema. Public wire JSON still requires explicit mapping and schema verification.

**Critical adoption test:** With representative existing product-owned persisted audit/event payloads and replay fingerprints, verify serializing and decoding round trips, map ordering, null handling, canonical payload identity and old replay behavior *before* changing mapper policy. Do not migrate stored JSON or inject polymorphic deserialization without separate review.

**Reliability semantics are unchanged:** Authenticate/authorize each attempt, then `JdbcIdempotencyPort.begin(request)`; only `ACQUIRED` executes product SQL using the **supplied Connection** inside `JdbcReliabilityTransaction.executeIdempotent(lease, IdempotencyResultCodec.strings(), work)`. Persist domain SQL, required event/audit intents and the replay result on one product-owned transaction. `REPLAY` requires reauthorization, `IN_PROGRESS` and `CONFLICT` require safe API responses. Never call an external service or manually commit inside the callback. The outbox is at-least-once compatible: consumers deduplicate and operators reconcile failed/DEAD claims. See [safe mutation guidance](../integration/jdbc-safe-mutation.md).

**Flyway:** Kernel JDBC still ships immutable V1–V3 migrations. The default `KernelJdbcMigrator` can collide with an application-owned `db/migration` location/history; do not invoke it blindly in a host with existing migrations. Decide one approved migration authority and test schema/history coexistence, clean install, replay and rollback before upgrade. See [host migration guidance](../integration/jdbc-migrations.md).

## 5. HTTP, observability and health

HTTP integration remains framework-neutral. Your HTTP framework validates request metadata, including duplicated/mixed-case tenant, correlation and authorization headers, and maps safe errors. A bearer-token extractor **extracts**; it does not validate JWT signatures, issuer or audience. Never use a caller-provided resource tenant ID as authoritative; scope actual SQL and respond safely to cross-tenant access.

`HealthAggregator.check(type)` remains synchronous. It converts exceptions to safe DOWN codes but imposes no deadline on blocking I/O. Your product must set bounded dependency timeouts and endpoint policy. An empty probe list reports UP by convention, not proof that downstream dependencies are healthy.

## 6. Upgrade acceptance checklist (0.3.2 → prospective 0.4.0)

Before a product opts in, record the actual artifact/source digests and product revision, then check:

1. **Published evidence:** Is `v0.4.0` signed, tagged, released and anonymously resolvable from Maven Central? Until yes, do not update production dependencies.
2. **Binary/build compatibility:** Compile and run the actual consuming Java 21+ application, inspect effective dependencies, and test old and new public call sites. Core-only consumers should remain free from JDBC.
3. **Authentication/tenancy:** Real verifier negative cases, unauthorized tenantless operations, tenant-owned resource rejection, tenant membership, module enablement, resource policy and tenant-filtered SQL.
4. **Input changes:** Valid/invalid module key grammar; exact 192/512/512 code-point idempotency boundaries and application HTTP error mapping.
5. **Durable path if selected:** Historical persisted codec/fingerprint replay; crash-atomic transaction, conflict, concurrent retries, loss of response, worker fencing, duplicates, DEAD recovery and time-bound keys.
6. **Database operations if selected:** Flyway V1–V3 history/ownership, product migrations, least-privilege runtime role, deployment drain, backup and restore/rollback; no automatic schema rewrite.
7. **Observability and deployment:** Safe correlation, privacy-aware telemetry, bounded readiness checks, and owner-approved independent deployment/rollback plan.

Document tests and gaps using the [consumer conformance specification](../integration/consumer-conformance.md). Source-level green CI and synthetic test fixtures are *not* production acceptance. IAM and File Storage retain their own adoption gates; do not assume a cross-product upgrade.

## 7. Common integration mistakes

| Symptom | Check / resolution |
| --- | --- |
| `RequestContextPipeline.tenantless(...)` or `JacksonRecordCodec(mapper)` not found | The installed artifact is likely still v0.3.2. Both APIs are **unpublished** at the time of this document. Do not switch coordinates until release. |
| Tenantless operation unexpectedly denied | It may be tenant-owned, have active tenant context or lack product authorization. Tenantless never means anonymous or unrestricted. |
| New module-key exception | Audit case/characters/length: lowercase ASCII letter first; then lowercase ASCII letters, digits, underscore, period, colon or hyphen; max 128. Do not conflate module enablement and resource permission. |
| Idempotency constructor rejects an old input | Enforce the 192/512/512 Unicode code-point contract at the application boundary; do not truncate keys or fingerprints silently. |
| Replayed output or JDBC JSON changes after mapper customization | Restore the previously verified mapper policy and compare stored payload/fingerprint fixtures before any rollout. |
| Flyway version/history conflicts | Stop rollout, inspect current schema history and resource locations; choose an application-approved migration plan. Never edit immutable V1–V3 bytes. |
| Readiness probe hangs | Apply bounded I/O and an endpoint-level timeout in the application; Kernel health aggregation does not interrupt suppliers. |
