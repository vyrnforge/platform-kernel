## 3. Interoperability rules and limits

- Use canonical snake_case properties, lowercase enum wire values, canonical lowercase UUIDv7 pattern for fields that require it, RFC 3339 UTC instants with Z suffix, and exact declared types. Opaque external file/resource/actor/subject IDs must not be coerced to UUIDs. UUIDv7 timestamp ordering is not a global monotonic sequence; IAM retains its local monotonic generator.
- Preserve required nullable keys: TenantContext.tenant_id; EventEnvelope.tenant_id/causation_id/actor; AuditEvent.tenant_id/actor; FileReference.owner_tenant_id. Optional nullable fields can be omitted or null as allowed by their schema. Do not convert missing required keys to valid null silently. Nested refs resolve within the same version directory; do not fetch an untrusted remote schema at request time.
- All eleven top-level schemas allow additionalProperties; consumers ignore unknown optional fields unless a specific contract states otherwise. Never infer permissions, claims or business meaning from an unknown property. Do not drop required known keys, reinterpret enum values or accept unsupported event semantics merely because JSON validates. Do not forward arbitrary sensitive fields.
- Validate serialized transport shapes, not default Java record names. Use a 2020-12-capable validator with format checks enabled where needed (date-time/uuid formats may be annotations depending on implementation); patterns and required/type constraints remain separate. Preserve integer precision (e.g. byte size and event version), reject invalid dates, and enforce runtime/product limits as well as JSON constraints.
- JSON Schema validates shape, not authority, ordering, durability, replay safety or transaction semantics. Tenant/resource consistency, authoritative lookup, actual issuer verification, membership and domain policy, effective entitlement, audit intent durability, deduplication and file access must be separately verified at product boundaries.
- Existing Java runtime is not an automatic wire validator: Java records use camelCase accessors/enums; some constructors reject blank strings or enforce extra consistency not expressed by minLength. EventEnvelope accepts domain DTOs but rejects obvious scalar/array shapes; JDBC validates serialized JSON object, other adapters must validate it. AuditEvent enforces tenant/resource consistency not encoded in cross-field schema. Trace propagation/HTTP rejects CR/LF and length violations, not full W3C grammar. Schema additional fields do not imply Java accepts or round-trips arbitrary properties. Runtime tightening in 0.3.2 is intentional; no schema bytes changed.
- API idempotency, event/audit intent ports, retry/lease/fencing, health, configuration and flags are Java mechanics/contracts, not additional released portable JSON schemas. Tenant-scoped API mutation idempotency is not event inbox dedup; generic inbox/task contracts remain research, not supported runtime. See [reliability semantics](reliability-semantics.md). Neither a shared database nor a specific broker/runtime is required.

## 4. Compatibility and evidence

Existing [compatibility script](../../scripts/check-contract-compatibility.py) checks v0.1's exact 13-file set and Git blob SHA-1 baseline, v0.2 matching set, normalized non-manifest text transformation of version paths, and exact approved manifest transformation (released status/version/date, DEC-K013, release notes). [Baseline file](../../contracts/compatibility/v0.1-git-blob-sha1.json). Existing protected main verification [43914381149](https://github.com/vyrnforge/platform-kernel/actions/runs/43914381149) passed; [release workflow](https://github.com/vyrnforge/platform-kernel/actions/runs/43663775552) verifies publication. This does not prove arbitrary cross-language parsing, format enforcement, semantic compatibility, live consumers or actual old/new behavior.

| Proposed future change | Compatibility review (no change authorized) |
| --- | --- |
| Add optional field | Usually additive; confirm both old receiver/new producer and new receiver/old producer, defaults/absence, privacy and semantic handling |
| New enum value or event type/version | Not automatically safe; old consumers may reject or misinterpret. Route/handle supported versions explicitly; do not silently reuse meaning |
| Remove/rename field, change type/meaning, optional→required | Breaking; new explicit contract version, migration/deprecation window, consumer owner review and rollback |
| Stricter validation / changed runtime semantics | Assess accepted old inputs and actual behavior separately; v0.3.2 already tightens validation without changing wire files |
| New language SDK or schema distribution | Demand, owner, maintenance and compatibility evidence first; separate authorization, no implied new JAR or package |

For a later authorized change: pin current producer/consumer schema and artifact revisions, test both rolling directions where applicable, include positive and negative examples, record actual observed results per CC-01/03/04 and applicable security/reliability cases, define upgrade/rollback and retirement owner. Keep both existing version directories immutable. No new version, executable fixtures or compatibility test changes in FAA-04.
