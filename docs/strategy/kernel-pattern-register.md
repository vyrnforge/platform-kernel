## 1. Purpose and evidence language

Collect recurring technical *guarantees* rather than matching class names. A similarly named retry method is not a shared contract if one operation is read-only and the other creates irreversible external effects. Conversely, a fencing invariant may be common despite different persistence implementations. This is a discovery register; **breadth does not confer implementation approval**.

- **Evidence S:** source-verified in released Kernel, contract or published docs at pinned revision. Does **not** establish live consumer acceptance.
- **Evidence C:** source-observed in other existing implementations / prior exact-revision research. Similarity is not yet proven semantic equivalence; see PR #47 for source pins, gaps and tested checkouts.
- **Evidence N:** current external standard/mature implementation used as a comparator, not as evidence of adoption.
- **Evidence H:** plausible repeatable requirement based on standards or architecture, without independently verified second use; do not invent a consumer or savings figure.
- **State BASELINE-GAP:** shipped contracts lack complete portable evidence. **HARDEN:** keep existing API and improve tests/guidance if separately authorized. **DESIGN:** research semantics, no runtime exists. **RESEARCH:** compare gaps/alternatives only. **DEPENDENT:** blocked on earlier research. **DEFER:** insufficient demand or unsuitable boundary.
- **P0/P1/P2/P3:** qualitative research order only. P0 protects the shipped foundation and adoption confidence; P1 investigates higher-value reusable contracts; P2 supporting opportunities; P3 lower-evidence/greater-boundary-risk candidates. No numerical ROI, SLA, implementation release or budget inferred.

## 3. Pattern falsification rules

A pattern is *not* shared merely because two implementations contain retries, UUIDs, a lifecycle class, a table named inbox or a similar HTTP controller. Require identical or intentionally composable failure guarantees and explicit scope. Reject or keep local when: domain policy/authority transfers to Kernel; a shared business DB or required synchronous service appears; optional JDBC becomes mandatory; raw provider claims or file grants become kernel authority; unknown third-party dependencies enter core; multiple versions must deploy together; or mature independent tooling already solves the need at lower total lifecycle cost.

Particularly do **not** treat: tenantless as IAM DEPLOYMENT; feature flag as permission; entitlement as resource authorization; EventIntentPort success as broker acknowledgement; API mutation idempotency as consumer inbox; an expired lease as cancellation of external side effects; a DEAD outbox row as proof of non-delivery; a FileReference as an access grant; JSON Schema validation as proof of cross-language behavioral parity; or synthetic test fixtures as actual consumer-owner acceptance.

## 4. Observation record template (copy per occurrence; no new issue automatically)

| Field | Required entry |
| --- | --- |
| Pattern ID / discovery state | Existing ID or proposed new ID; Discover / Design / Experiment / Promote / Adopt |
| Source | Product/repository and exact revision/actual checkout, source path/API, issue/PR; redact secrets |
| Observed guarantee | Inputs, outputs, state owner, transaction, retry/failure assumptions, scope and privacy |
| Counterexample | Same named helper with different semantics; at least one failure case that could invalidate abstraction |
| Similarity verdict | Equivalent / overlapping only / different / UNKNOWN; note independent evidence vs same-session reasoning |
| Alternatives | Product-local, existing library/framework, tiny pure contract, optional adapter, shared service only if approved |
| Lifecycle and compatibility | Adapter work, dependencies, maintenance owner, immutable data/version, old/new consumer effects |
| Evidence and acceptance | Real sample size/window, negative tests, actual observations, mandatory conformance and owner |
| Decision | Retain local / research / bounded experiment proposal / reject / promotion request; date and approver |
| Reopen trigger | Change in consumer revision, semantics, failure evidence, standard or demand |

**Trigger intake** when a second independent implementation repeats a guarantee, a failure reveals an omitted invariant, an adapter is repeated, a breaking upgrade is proposed, portable clients disagree, or a standards/mature-tool change creates measurable simplification. Source comparisons are read-only unless separately authorized. A first occurrence may justify design research (DEC-K021), **not** production promotion.

## 5. Invariants for any future promotion

1. Product owns business state/authorization, file bytes/grants, native IAM and authoritative evidence. Kernel is embedded by default, framework-neutral Java21 core, optional JDBC and testkit (three existing JARs).
2. Contracts are versioned; preserve released v0.1 historical/v0.2 wire files, V1–V3 SQL and v0.3.2 until separately approved compatibility plan. Verify Java API + wire + behavioral + persisted data compatibility, both rolling directions.
3. At-least-once events, receiver-side dedup, current authorization before retry/replay, tenant isolation, atomic product mutation/required intents/idempotency result, fenced current owner and explicit recovery remain mandatory where applicable.
4. Actual two-consumer evidence and E1b/K2 equivalence remain mandatory for IAM generic reliability/lifecycle extraction and optional JDBC replacement under ADR-0085. Independent consumer-owner/QA/Security acceptance cannot be replaced by synthetic tests or a documentation review exception.
5. Require demand, owner, alternatives, upgrade independence, complete development/integration/migration/verification/maintenance/operations costs, measurable benefit and approved release/rollback criteria before Promote. Research and contract designs alone do not authorize experiments or new packages.
