## B. RD-01 — Event inbox / deduplication research brief

Owner API/Integration; Backend/Data, Security, QA, Architecture and actual consumer owners review. Problem: at-least-once receiver retries may duplicate authoritative effects or lose processing after premature acknowledgement. **Confirmed evidence:** IAM JdbcInboxRepository.tryAccept inserts RECEIVED on unique (tenant_id, consumer_name, message_id), returns false on conflict; markCompleted updates only RECEIVED. Existing PersistenceFoundationIntegrationTest.inboxDeduplicatesPerTenantConsumerAndMessage covers key separation, not atomic business effect/crash recovery. Source method does not compare content fingerprint or itself wrap handler/ack. Need actual caller transaction/lifecycle evidence; RECEIVED duplicate is not automatically safely completed. Storage JdbcOperations.enqueue and completion digest provide domain-specific work dedup, not independent generic event inbox evidence. Kernel EventEnvelope + outbox is producer side; API mutation idempotency is distinct.

**Proposed contract design, no new API/schema:** scoped receiving identity = consumer namespace + verified scope (tenant UUID or explicitly permitted tenantless partition) + stable event ID; producer/event type/version and canonical content fingerprint bound to identity so mismatched content conflicts/quarantines, not silently duplicates. Explicit tenantless representation with uniqueness/isolation (SQL NULL uniqueness trap); no deployment fallback. Authenticate transport, validate envelope/authority before acceptance; compare current policy where business action requires it. For a local durable handler, insert/claim receipt, mutate domain, write required intents and completion in one owning transaction; ack only after durable commit. If async receipt is committed separately, RECEIVED/IN_PROGRESS requires recoverable ownership and completion proof; never ack as completed solely on key existence. Duplicate completed same content acknowledges without second business effect; conflicting content fails safely; transient rollback permits retry; bounded retry/poison handling and operator reconciliation. External I/O outside DB tx, durable intent plus idempotent external key/reconciliation. Retention ≥ agreed replay/redelivery horizon; expiry and restore gaps explicit, no indefinite exactly-once promise. Persist minimal safe evidence, no raw secrets; propagate tenant/correlation and event ID causation. No generic scheduler or broker assumption.

| Option | Benefit | Limitation / recommendation |
| --- | --- | --- |
| Retain product-local transactional inbox / idempotent upsert | least new dependency and authority risk | duplicated semantics if real second use; preferred today |
| Framework-neutral contract and optional adapter later | reusable invariants and conformance, no mandatory runtime | maintenance, migration and collision/retention semantics; only after demand + evidence |
| [Spring Integration idempotent receiver](https://docs.spring.io/spring-integration/reference/7.0/handler-advice/idempotent-receiver.html) / [metadata store](https://docs.spring.io/spring-integration/reference/meta-data-store.html) | mature duplicate selection and persistent stores | framework coupling, default memory not restart-durable, atomicity with product mutation must be established; evaluate where already Spring, not core dependency |
| [Kafka transactions](https://kafka.apache.org/design/) | offsets + Kafka output transaction in Kafka-native pipeline | external DB/side-effect coordination still required; no broker mandate, not substitute for local transaction |

**Proposed acceptance for a future bounded experiment (not authorized):** RD1-AC01 concurrent same scoped key/content → one committed business effect; separate tenants/consumer namespaces independent, explicit tenantless key. RD1-AC02 same key different content → conflict/no effect; untrusted tenant/issuer/unsupported version rejected. RD1-AC03 rollback before commit → retry; commit before ack then crash → duplicate no effect; receipt committed without effect → recover not discard. ## C. RD-02 — Retry, deadline, lease, fencing research brief

Owner Backend/Domain; Reliability/Data, QA, Security, Architecture and consumer owners review. Confirmed common need: workers claim bounded work and handle failure without stale state updates. Kernel JdbcOutboxPublisher uses per-row token, expiry and PENDING predicate before send and update; max attempts, fixed retryDelay, expired final claim DEAD. A successful transport followed by update failure can be uncertain. Storage OutboxDelivery wraps it; JdbcOperations separately uses per-batch token paired with operation/tenant, expiry, bounded kind-specific claims, attempts and permanent/transient outcomes; same-connection finish for metadata; external provider effects are not fenced by DB token. IAM native outbox source gap F41-03 above; scheduled work uses lease owner+expiry, connector WorkerLease includes id+epoch+expiry. Different states and business effects, not interchangeable. IAM lifecycle engine is not a job engine.

**Proposed invariants, not new contracts:** separate attempt budget, next eligible time, overall deadline and per-attempt timeout/lease; clock injection and precision/clock-skew policy, deadline vs lease expiry independent. Define retryable/permanent/uncertain outcomes in product, bounded exponential/jitter policy only where appropriate, no retry after deadline/budget, avoid retry amplification; no network work in authoritative tx. Claim identity unique per acquisition (opaque token or monotonic epoch scoped to work); update/renew/complete/reschedule checks tenant/work/current token or epoch/unexpired lease atomically; same-worker reacquire invalidates old token. Bound batch/concurrency and timeouts; release DB locks before I/O. Final expired claim terminal without extra send; uncertain delivery remains possible. Fencing guards authoritative store, not external service unless it participates; use stable external idempotency key or reconcile before retry. Cancel/timeout is not proof remote work stopped. Preserve domain-specific revision/configuration pins, authorization and operation kinds; no generic task/job state machine promotion.

| Option | Benefit | Limitation / recommendation |
| --- | --- | --- |
| Retain local SQL + current Kernel JDBC outbox | proven existing boundary, simple deployment | local differences and fencing gap need targeted evidence; preferred baseline |
| Shared pure retry/deadline/claim invariants | lower conceptual duplication | requires semantics/clock precision/failure equivalence; proposed research only |
| [Resilience4j Retry](https://resilience4j.readme.io/docs/retry) / [TimeLimiter](https://resilience4j.readme.io/docs/timeout) | mature per-call attempt, interval, predicate and timeout decorators | not durable lease/transaction/fencing or remote cancellation proof; use at product edge if selected, not mandatory core dependency |
| Broker/managed durable workflow | mature scheduling/recovery for justified complex work | operational cost, authority/migration coupling; defer absent demand, no workflow runtime in Kernel |

**Future acceptance proposal:** RD2-AC01 bounded claims, no overlapping active owners; expiry A→B, late A update/renew/complete denied, including same-owner reuse and exact expiry boundary; wrong tenant/token denied. RD2-AC02 retryable/permanent/uncertain with max attempts and deadline, final expired claim no extra send; bounded jitter/delay and clock skew/precision. RD2-AC03 failure before/after send/commit; stale completion rolls back product mutation/intent; no external duplication assumption; reconcile receiver/provider. RD2-AC04 restart/restore and old-writer drain, historical replay, measured RPO/RTO, no dual stores; verify safe logs and bounded load. RD2-AC05 compare local/optional shared/mature alternatives, actual second consumer need, maintenance/cost and independent verification. **Recommendation:** prioritize F41-03 local owner review and invariant design; defer generic task contracts (RD-03 depends on RD-01/02), generic scheduler/job runtime, migration and promotion. Proposed future isolated experiment only after approved scope/ADR gate; test exact same fault timeline across existing adapters and optional contract candidate, no production data. E1b/K2 not authorized.
